## A. Current architecture

### A.1 Shape of the system

This is **not** a framework application. It is a static site plus seven Vercel serverless functions, with **the entire business database stored as a single JSONB blob in one Postgres row**.

```
Browser (admin.html + assets/admin.js, 9,117 lines)
   |
   |  entire application state, serialized as one JSON document
   v
PUT /api/state  --> reconcileReservations() --> validateAppState()
   |                                                  |
   |                                                  v
   |                        Supabase REST (service_role key, server-side only)
   |                                                  |
   v                                                  v
                          public.app_state  WHERE id = 'production'
                          (columns: id, state jsonb, updated_at, updated_by)
```

There is exactly **one row** in `app_state`, keyed `'production'` (`api/_lib/kombu-backend.js:5`). Products, ingredients, packaging, suppliers, partners, recipes, batches, sales, orders, receipts, deliveries, leads, purchases, expenses, cost sources, CMS content, settings and the audit trail are all fields inside that single JSON document. There are no relational tables for business data, no foreign keys, no per-entity writes.

There is **no `package.json`**, no lockfile, no dependency manifest, no test runner, no linter, no CI. The only vendored dependency is `assets/vendor/jspdf.umd.min.js`, committed directly.

### A.3 The complete write path (user action → persisted result)

This is the flow the audit brief asked for, traced end to end:

1. **User acts** in the admin (e.g. confirms a delivery). A handler in `bindModuleEvents`/`handleAction` mutates the in-memory `state` object directly.
2. **Cascading client-side recalculation** fires synchronously — e.g. `registerOrderDelivery` (`admin.js:2691`) calls `consumeDeliveryReservation` → `refreshOrderReservationStatus` → `syncOrderIntegrations` → `syncOrderSales` → `reconcileOrderReservations` → `refreshOrderReservationStatus` again.
3. **`saveState()`** (`admin.js:1089`) writes the whole state to `localStorage`, then calls `scheduleCloudSave()`.
4. **Debounced 800 ms**, then `pushStateToCloud()` (`admin.js:1099`) `PUT`s `{ state, updatedAt }` — the *entire* document — to `/api/state`.
5. **Server** verifies the session cookie, re-runs `reconcileReservations()` over the client-supplied state, runs `validateAppState()` (shape and size only), then `replaceAppState()`.
6. **Optimistic concurrency**: `PATCH app_state WHERE id='production' AND updated_at = <client's updatedAt>`. Zero rows affected → `409 state_conflict`.
7. **Server returns the reconciled state**, and the client replaces its in-memory state with it, then re-renders.

**The critical property of this design: the server never validates business rules.** It checks that arrays are arrays and that the blob is under 5 MB. Every invariant — stock never negative, reservations ≤ physical stock, costs correct, orders not corrupted — is enforced *only* by client-side JavaScript. A bug in `admin.js` writes straight through to production with no backstop. This is the single most important structural fact about the system.

### A.4 Authentication and sessions

- One shared password (`ADMIN_PORTAL_PASSWORD`), compared with `crypto.timingSafeEqual` after a length check (`api/auth/login.js:23-27`).
- On success, an HMAC-SHA256-signed token is set as `kombu_admin_session`: `HttpOnly`, `SameSite=Lax`, `Secure` (off only for localhost), 12 h `Max-Age`, and a 12 h `exp` inside the payload (`kombu-backend.js:337-354`).
- Signing key is `ADMIN_SESSION_SECRET`, falling back to an HMAC derived from `SUPABASE_SERVICE_ROLE_KEY` (`kombu-backend.js:298-308`). The fallback is safe but couples session validity to the Supabase key — rotating that key logs everyone out.
- `SameSite=Lax` means cross-site `POST` does not carry the cookie, so classic CSRF against `/api/state` is **not** exploitable. This is load-bearing and should not be relaxed.
- **The role selector in the admin UI is decorative.** `canWrite()` (`admin.js:1240`) branches on a client-side `currentRole` variable that the user can change; the server issues exactly one role, `"Owner / Admin"`, and `requireAdmin` does no role check at all. Anyone with the password has full write access to everything.

## B. Production data architecture

### B.1 Where data lives

| Store | Contents | Access |
|---|---|---|
| `public.app_state` (1 row, `id='production'`) | **All business data**, as JSONB | Server-only, via `service_role` key. RLS enabled with **no policies** — correct: nothing but the service role can read it. |
| `public.email_events` | Nothing | Table exists in `supabase/schema.sql:20` but **no code ever reads or writes it**. Dead schema. |
| Storage bucket `public-media` | CMS/product images | `public = true`, 10 MB cap, MIME-restricted at bucket level. Public read policy; writes server-side only. |
| Browser `localStorage` (`kombu-admin-state`) | Full mirror of the state blob | Per-device cache; also the boot-time source of truth before cloud sync completes. |

### B.2 Concurrency model

Optimistic locking via `updated_at` string equality (`kombu-backend.js:207-222`). Two code paths bypass it:

- `replaceAppState(state, by, "")` with an **empty** `expectedUpdatedAt` falls through to `upsertAppState` — an unconditional overwrite of the entire production document with **no concurrency check at all** (`kombu-backend.js:209`).
- `mutateAppState` (used by `/api/lead` and the cron) does read-modify-write with up to 4 retries. This one is correct.

The concurrency check protects the *transport*, but because the payload is always the whole document, a successful write by user A followed by a successful write by user B still means B's document wholly replaces A's. There is no field-level merge anywhere. Two people editing different modules at the same time will silently clobber each other unless the `updated_at` guard happens to fire.

### B.3 Backups, migrations, recovery

- **No backup mechanism exists in this repository.** No export job, no snapshot table, no point-in-time copy. Recovery depends entirely on whatever Supabase's plan-level PITR/backup retention is for this project — which must be verified in the Supabase dashboard, because with a single-row design, one bad write destroys everything and the only recovery is a database-level restore.
- **No migration mechanism.** Schema changes happen implicitly, inside `normalizeState()` (`admin.js:987`), in the browser, at page load. This is why `AUDIT-`-style defensive parsing is scattered through the code (`item.actual ?? item.inventoryQty ?? item.actualYield ?? item.quantity`).
- **No state versioning.** The blob has no schema version field. `settings.priceVersion` exists but governs a single price migration, not the document shape.

### B.4 Enumerated corruption scenarios

Each of these is reachable in the current code; the ones with a finding ID are detailed in §D.

| Scenario | Reachable? | Reference |
|---|---|---|

| Stale browser state replaces newer server state | Yes | C2 |

### 🔴 CRITICAL

#### C1 — Stored XSS in the admin Leads module, injectable by any anonymous internet user

**Where:** `assets/admin.js:5238-5251` (`renderLeads`), reached from `api/lead.js` → `normalizeLead` (`api/_lib/kombu-backend.js:75-97`).

**What.** `/api/lead` is a public, unauthenticated `POST` endpoint. `normalizeLead` only trims and truncates its input — `cleanText` is `String(value).trim().slice(0, max)`, with no HTML escaping. The values are persisted verbatim into `state.leads`. `renderLeads()` then interpolates them straight into `innerHTML`:

```js
<td><strong>${lead.name || "Sem nome"}</strong><br><span>${lead.whatsapp || "Sem WhatsApp"}</span></td>
<td>${lead.business || "-"}<br><span>${lead.businessType || ""}...</span></td>
<td>${lead.instagram || "-"}</td>
<td>${lead.message || "-"}</td>
```

None of these pass through `escapeHtml`, even though the file defines and uses `escapeHtml` 162 times elsewhere. The `table()` helper (`admin.js:4110`) joins raw row HTML and does not escape either. Additionally `lead.id` is **client-supplied and never sanitized at all** (`normalizeLead` does `id: lead.id || ...` without `cleanText`) and is interpolated into an attribute: `data-lead-status="${lead.id}"`.

**Why it matters.** The admin page holds the session cookie and can `PUT` arbitrary content to `/api/state`. Script executing in that page has **complete control of the entire production dataset** — it can read every order, customer, price and cost, and it can overwrite the whole blob. There is no CSP to contain it.

**How it fails.** Anyone posts:
```
POST /api/lead   {"lead":{"name":"x","message":"<img src=x onerror=fetch('/api/state').then(...)>"}}
```
The lead is stored. The next time you open the Leads module, it runs.

**Production data at risk:** Yes — total compromise, both exfiltration and destruction.

**Fix.** Escape at render (`escapeHtml` on every interpolated lead/partner field), sanitize `lead.id` server-side with `cleanText`, and add a `Content-Security-Policy` header in `vercel.json` as defence in depth. **Risk of fixing: very low** — it is presentational, additive, and touches no persistence logic.

#### C2 — After a 409 conflict, the client adopts the server's new version token but keeps its stale data, so the *next* save silently destroys the other device's work

**Where:** `assets/admin.js:1135-1140`, interacting with `1153-1157` and `1099-1100`.

**What.**
```js
} else if (response.status === 409) {
  const payload = await readJsonSafe(response);
  cloudSyncEnabled = false;
  cloudSyncLastError = "Existem alterações mais recentes na nuvem. Recarregue o painel...";
  cloudStateUpdatedAt = payload.updatedAt || cloudStateUpdatedAt;   // <-- takes the NEW token
}
```
The conflict handler refreshes `cloudStateUpdatedAt` to the server's *current* value while leaving the local `state` untouched and stale. It sets `cloudSyncEnabled = false` — but **neither `scheduleCloudSave()` nor `pushStateToCloud()` ever checks `cloudSyncEnabled`**; both gate only on `cloudSyncReady`, which is still `true`.

**How it fails.** Phone saves order A. Laptop (open since before that) saves order B → `409`, shows a warning banner telling the user to reload. The user does not reload; they type one more character anywhere. `saveState()` → 800 ms later `pushStateToCloud()` sends the stale laptop state with the *freshly adopted* `updatedAt`. The `PATCH ... WHERE updated_at = <that value>` now **matches**, the write succeeds, and the phone's order A is gone. The optimistic-concurrency guard has been converted into a rubber stamp by its own error handler.

**Production data at risk:** Yes — silent, unrecoverable loss of another device's work, with no error shown after the initial banner.

**Fix.** On `409`, do not adopt the server token. Either freeze saving until an explicit reload/merge, or re-fetch and force the user to reconcile. **Risk of fixing: low**, but it changes save behaviour under conflict and must be tested with two sessions.

#### C3 — The "no version token" path is an unconditional overwrite of the whole production document

**Where:** `api/_lib/kombu-backend.js:207-209`, reached from `assets/admin.js:1216-1224`.

**What.** `replaceAppState` falls back to a blind upsert when `expectedUpdatedAt` is empty:
```js
if (!expectedUpdatedAt) return upsertAppState(state, updatedBy);
```
`syncFromCloud` sets `cloudStateUpdatedAt = payload.updatedAt || ""`, and if `payload.exists` is falsy it immediately calls `pushStateToCloud()` — pushing the browser's `localStorage` contents with an empty token, which becomes an unconditional overwrite. `getStateRow()` returns `Array.isArray(rows) ? rows[0] || null : null`, so **any response that yields an empty array** — a PostgREST hiccup, a transient read failure that still returns `200`, a momentary RLS/permission change — produces `exists: false` and arms this path.

**Why it matters.** This is the "stale browser state replaces newer server state" scenario in its worst form: no conflict check, no warning, entire business database replaced by one browser's cache.

**Production data at risk:** Yes — catastrophic, single-step, total.

**Fix.** Never bootstrap-write from a client cache. Require an explicit, deliberate action to create the row when it genuinely does not exist, and treat `exists:false` on a system known to have data as an error state, not an invitation to write. **Risk of fixing: low.**

### 🟠 HIGH

#### H1 — `GET /api/state` writes to production (currently deployed)

**Where:** `api/state.js` at `HEAD` (this is exactly what the uncommitted change is fixing).

The deployed `getReconciledState()` reconciles the state on **read** and, if anything changed, persists it with up to 4 retries. A read endpoint mutates the production database. Every admin page load, every tab refresh, can rewrite the entire blob. This also means read traffic competes for the optimistic lock.

**Risk:** high. **Note:** the uncommitted working-tree version removes this. That part of Codex's change is a genuine improvement and should be preserved when the rest is finished.

#### H2 — Merely opening the admin panel rewrites production state

**Where:** `assets/admin.js:622-645`, `987-1077`, `1217-1221`.

`syncFromCloud()` loads the cloud state, then calls `runStartupIntegrations()`, which runs `syncPurchaseExpense` for every purchase, `syncOrderIntegrations` for every order, and `reconcileOrderReservations()` across all open orders — then calls `saveState()`, which schedules a cloud push. `normalizeState()` additionally injects 300 ml product/recipe variants and packaging seeds on every load.

Consequence: **there is no read-only mode.** Looking at the dashboard is a write. Combined with H3/H4 below, opening the panel actively rewrites sales, partners and expenses.

#### H3 — Order-derived sales are destroyed and regenerated on every page load

**Where:** `assets/admin.js:3668-3669`.
```js
function syncOrderSales(order) {
  state.sales = state.sales.filter((sale) => sale.orderId !== order.id);
  ...  // then re-creates them with brand new id("sale") values
```
Since `runStartupIntegrations` calls this for every order at boot, every sale that originated from an order is deleted and recreated **with a new random ID** on every admin load. Any manual correction to such a sale — a price fix, a discount, a note — is silently reverted. Sale IDs are not stable identifiers and cannot be referenced by anything.

#### H4 — Manually edited partners and expenses are overwritten from order/purchase data on every load

**Where:** `assets/admin.js:3617-3642` (`syncOrderPartner`), `3760-3776` (`syncPurchaseExpense`).

Both use `Object.assign(existing, payload)`, unconditionally overwriting `neighborhood`, `city`, `whatsapp`, `instagram`, `flavors`, `terms` on the matched partner, and `category`, `description`, `amount`, `method`, `recurring` on the matched expense. Partners are matched by normalized name, so two customers with the same business name merge into one record.

#### H5 — Historical costs are not snapshotted; changing an ingredient price rewrites past financials

**Where:** `assets/admin.js:1743-1750` (`batchCost`), `1773-1778` (`totals`).

`batchCost()` recomputes from the **current** recipe and **current** ingredient prices. `totals().cogs` multiplies each historical sale by that live figure. Raising a supplier price today retroactively changes last quarter's COGS, gross profit and margin.

This directly violates the invariant your own `ARCHITECTURE.md` states ("Each production batch must store a snapshot ... Future price changes must update future estimates only") — the rule is documented but **not implemented**.

Worse, the recipe lookup falls back to an arbitrary record:
```js
const recipe = byId("recipes", batch.recipeId) || state.recipes.find(r => r.flavor === batch.flavor) || state.recipes[0];
```
A batch whose recipe was deleted is costed using **whatever recipe happens to be first in the array**, silently.

#### H6 — Batch codes are generated by counting, so deleting a batch produces duplicate codes

**Where:** `assets/admin.js:1623-1630`.
```js
const existing = state.batches.filter((b) => String(b.code||"").startsWith(prefix)).length;
return existing ? `${prefix}-${existing + 1}` : prefix;
```
With codes `X`, `X-2`, `X-3` (count 3, next would be `X-4`), deleting `X-2` drops the count to 2 and the next generated code is **`X-3` — a duplicate**.

Batch code is the join key for sales (`netSalesForBatch`), allocations (`batchesByCode`), and stock. `remainingByBatch` is built with `new Map(eligibleBatches.map(b => [code, ...]))`, so a duplicate key **silently discards one batch's entire produced quantity**. Stock vanishes. `nextReceiptNumber` (`admin.js:1930`) has the same count-based flaw.

#### H7 — An empty-string `actual` on a batch zeroes its stock and silently releases every reservation against it

**Where:** `api/_lib/reservations.js:168-172`, mirrored at `assets/admin.js:1346`.
```js
nonNegative(batch?.actual ?? batch?.inventoryQty ?? batch?.actualYield ?? batch?.quantity)
```
`??` only falls through on `null`/`undefined`. An empty string from a cleared form field is neither — so `""` short-circuits the chain, `Number("")` is `0`, `isEligibleBatch` returns `false`, the batch drops out of `eligibleBatches`, and every allocation pointing at it is dropped on the next reconcile. Stock and reservations disappear with no error and no audit entry explaining why.

#### H8 — Closing an order erases which batch fulfilled it

**Where:** `api/_lib/reservations.js:509-522` + `315-333`.

For every order, `item.allocations = []` is executed unconditionally. Allocations are only re-added for **open** orders. For a closed order (`entregue`/`concluido`/`cancelado`), `updateItemReservationFields(item, true)` then sets `reserved = 0`, `batchCode = ""`, `readyDate = ""`.

So the moment an order is delivered, the lot-traceability link on the order is destroyed. For a beverage producer this is a food-safety/recall concern. The information survives only in `state.sales[].batchCode` — and H3 means those sale records are themselves torn down and regenerated on every page load.

#### H9 — Client and server implement the reservation engine twice, with different vocabularies

`assets/admin.js` and `api/_lib/reservations.js` are two independent implementations of allocation, FIFO ordering, flavor matching, size inference and status derivation. They disagree:

| | Client (`refreshOrderReservationStatus`) | Server (`updateItemReservationFields` / `updateOrderStatus`) |
|---|---|---|
| item fully done | `"entregue"` | `"concluido"` |
| item partly reserved | `"em produção"` | `"parcial"` |
| order fully delivered | `"entregue"` | `"concluido"` |

Each rewrites the other's output on every round-trip. And `orderProductionRows()` (`admin.js:2359`) filters with `!["entregue","cancelado"].includes(order.status)` — which **does not match `"concluido"`**, so an order the server closed still appears as outstanding production demand.

#### H10 — Client and server disagree on which batches count as stock

`finishedStockRows()` (`admin.js:1758`) excludes only `"planejado"` and `"descartado"`, by exact string comparison. The server's `INELIGIBLE_BATCH_STATUSES` also excludes `bloqueado`/`blocked`, and normalizes case/accents first. A blocked batch therefore shows as sellable stock in the UI while the server refuses to reserve from it; a batch stored as `"Planejado"` counts as stock client-side and not server-side.

#### H11 — `deliveredQty` can never decrease, so a mis-entered delivery cannot be corrected

**Where:** `assets/admin.js:1017`.
```js
deliveredQty: Math.max(Number(item.deliveredQty || 0), Number(deliveredByItem[key] || 0))
```
`normalizeState` takes the max of the stored value and the sum of deliveries, so removing or reducing a delivery record leaves `deliveredQty` at its high-water mark. Outstanding quantity stays understated, and the corresponding reservation is released permanently.

#### H12 — The uncommitted working-tree change breaks the reservation regression suite and is only half-implemented

**Files:** `api/state.js`, `api/_lib/reservations.js` (modified, uncommitted).

I ran both offline suites against the committed `HEAD` in an isolated copy and against the working tree:

| Suite | `HEAD` (`cfd7c6c`) | Working tree |
|---|---|---|
| `scripts/reservation-regression.js` | ✅ 14/14 scenarios | ❌ fails `testNewProductionUsesLegacyOrderIdentity` (`0 !== 10`) |
| `scripts/api-regression.js` | ✅ pass | ✅ pass |

The change introduces three modes — `preserve` (new default), `allocate-new-stock`, `recalculate` — implementing item #3 of your Codex brief. Two problems:

1. **`admin.js` never sends `reservationMode`.** I verified this directly: 0 occurrences of `reservationMode`, `allocate-new-stock` or `recalculate` in the client. So every save would land in `preserve` mode and the server would **stop auto-allocating new production to orders entirely** — while the client still does the aggressive `reconcileOrderReservations()` teardown-and-rebuild on every boot (H2). The two halves would be pulling in opposite directions, and the server would no longer be a safety net.
2. **The failing test is the correct alarm**, not a stale expectation: it asserts that new production reaches an open legacy order. Under `preserve` it does not, because the client is supposed to have asked for `allocate-new-stock` and does not know how.

**Recommendation: do not deploy these two files as they stand.** The direction is right (especially removing the write-on-read in H1); it needs the client half plus updated test expectations.

#### H13 — No rate limiting on the public lead endpoint or on admin login

- `/api/lead` is unauthenticated and each call does a full read-modify-write of the **entire production state document** via `mutateAppState`, plus a Resend email. It is a cheap amplification vector against your database and your email quota.
- `appendLeadToState` keeps `state.leads.slice(0, 500)` — so ~500 junk submissions **evict every real lead** from the CRM.
- `/api/auth/login` has no attempt limiting against a single shared password.

## F. Technical debt

1. **Single-blob persistence.** Everything is one JSON document. This forecloses per-entity concurrency, per-entity permissions, indexed queries, partial writes, and row-level audit. It is the root cause of C2, C3 and B.2. It is *not* urgent to replace — it works at current scale — but it caps how safely the system can grow.
2. **The server does not own the business rules.** `validateAppState` checks shapes and size, nothing else. The client is the only enforcement point for every invariant you listed in the brief. This is the reason a frontend bug *can* silently corrupt persistent data — the exact scenario you asked me to rule out. I cannot rule it out; it is the current design.
3. **Duplicated reservation engine** (H9). Two implementations, already divergent, each overwriting the other.
4. **`admin.js` is a 9,117-line module** with no boundaries between data access, business rules, and DOM rendering. `escapeHtml` discipline is good in most of it and absent in exactly the places that matter (C1) — a predictable outcome of manual repetition rather than a rendering layer.
5. **Derived data stored as if it were source data.** Sales, expenses and partners are recomputed from orders/purchases *and* stored, so "recompute" and "user edit" fight each other on every load (H3, H4).
6. **Documentation drift.** `ARCHITECTURE.md` describes cost snapshotting as a rule; it is not implemented (H5). `AUDIT_REPORT.md` calls lead persistence "atomic" and states that manual reservation targets "reconcile immediately without exceeding real stock" — the reconcile path does clamp to stock, but the surrounding claims describe intended, not actual, behaviour. `README.md` says the app is "currently a static site ... will also serve the serverless function in `api/lead.js`", which understates the seven functions now present. Treat all four as historical.
7. **No dependency manifest, no CI, no runnable browser tests** (M15).

## I. Proposed engineering workflow

**Ground rules I will follow from here:**

1. **Never push directly to `main`.** Assume every push to `main` deploys to production instantly until §C.2 proves otherwise.
2. **One concern per branch and per commit.** No mixing a bug fix with a refactor.
3. **Before every change:** `git fetch && git pull --ff-only`, re-read the current file (Codex and you edit in parallel — I will never revert or overwrite work I did not write), and stage only my own paths.
4. **Before every push:** run `node scripts/reservation-regression.js` and `node scripts/api-regression.js`, then read the complete diff myself and confirm nothing unrelated crept in.
5. **Never test against production data.** Once §C.2 is answered, all validation happens in preview or a separate Supabase project. If a production smoke test is genuinely unavoidable, it will be read-only, narrowly scoped, and I will tell you exactly what it touches beforehand.
6. **Every data-affecting change ships with a rollback path** stated up front — for code, the revert commit; for data, an explicit backout plan and a pre-change export.
7. **Backward compatibility is assumed, not hoped for.** Any change to a data structure must parse records written by older code. New fields are optional with defensive defaults; nothing is ever required retroactively.
8. **I report what I find, including bad news.** If I discover that historical data is already inconsistent, I will tell you and propose a reconciliation strategy — I will not quietly repair production records.

```
pull main  ->  branch  ->  smallest correct change  ->  run both suites
   ->  self-review full diff  ->  push branch  ->  preview deploy
   ->  validate the affected workflow  ->  your approval  ->  merge
   ->  post-deploy smoke test  ->  report exactly what changed
```

**Two things I need from you before I write any production code:**
1. The Vercel answers in §C.2 — above all, **whether preview deployments write to the production Supabase project**.
